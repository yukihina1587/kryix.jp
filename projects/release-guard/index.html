06 / PROJECT DETAIL

Release Guard

Webアプリを更新したあとも、すでに利用中の人が操作を続けられるか。Release Guardは、ブラウザのタブを開いたままデプロイし、旧版と新版の操作・通信を比較する、開発者向けのコマンドラインツールです。

技術スタック

  • TypeScript
  • Node.js 24
  • Playwright
  • Chromium
  • Amazon CloudFront
  • Vite
  • GitHub Actions

01

解きたかったこと

管理画面を朝から開いていた人が、午後の更新後に「詳細を見る」を押したら画面が動かなくなる。一方で、更新後にサイトを開き直した人には問題がない。古い画面が後から必要とするJavaScriptを、新しいデプロイで削除してしまうと、このような不具合が起こり得ます。

新しく開いた画面だけの動作確認では見逃すため、更新前のタブを実際に生かしたまま、更新をまたいで操作する仕組みを作りました。

02

どういうときに使う？

  • S3＋CloudFrontで配信するReact／Viteの管理画面や会員向けSPAを更新するとき
  • デプロイ時の古いファイルの削除方法や、HTML・JavaScriptのキャッシュ設定を見直したとき
  • ステージング環境のリリース確認をCIへ組み込み、利用中の画面と新規アクセスの両方を毎回確かめたいとき

03

使い方と検証の流れ

最初はREADMEのセットアップ後に npm run demo を実行すると、AWS認証やクラウドリソースを用意せず、正常な更新と不具合のある更新を手元で試せます。

  • 準備：HTMLにビルドIDを埋め込み、新版のVite manifestと成果物を用意。設定JSONにURL、クリックする要素のdata-testid、期待する表示、遅延ロードするJSを指定する
  • 更新前：validateで設定と成果物を確認。runを開始すると、旧版でシナリオが成立するかを確かめ、更新を待つ別のタブを開いて保持する
  • 更新：runから利用者の既存デプロイコマンドを1回実行。保持した旧版タブで指定の操作を続け、新しく開く画面でも新版の表示と操作を確かめる
  • 確認：旧版／新版の成否と通信の証拠をHTML・JSONレポートで確認。CIでは終了コード0が合格、1が不具合検出、2が設定不備や検証未完了を表す

04

何が分かるのか

  • 旧版で必要なJavaScriptが403／404になったり、通信に失敗したりしていないか
  • JavaScriptやCSSのURLに、エラーページやSPAのHTMLが返っていないか
  • 公開待ちの期限までに期待するビルドIDが見えるか、新版の対象アセットが手元のmanifestと整合するか
  • 「旧版だけ失敗」「新版も失敗」「事前確認で停止」を区別し、調査する箇所を絞るための材料を残す

05

設計と工夫

  • 旧版のJavaScript状態を保持するため、ブラウザをデプロイ前後で同じプロセス内に生存させる。動作確認用と保持用のタブを分け、検証前に遅延ロードを消費しない
  • キャッシュ無効化や通信の差し替えを行わず、実際に観測した応答を判定に使う。先読み済みで検証が成立しない場合も、成功とは扱わない
  • CloudFront設定の参照は任意。読み取りAPIからキャッシュポリシーなどを調べ、403／404という事実と、削除・権限・配信設定といった原因候補を分けて説明する
  • レポートにはレスポンス本文、Cookie、認証ヘッダーを保存せず、外部通信しない静的HTMLを生成する

06

実装と検証の状況

2026年10月31日時点で、ブラウザ検証・設定検証・レポート・任意のCloudFront設定参照を含む初期実装をGitHubに公開しています。

  • ローカルデモで「旧版ファイルを保持して成功」「旧版JSが404で失敗」「JSの要求にHTMLが返って失敗」の3ケースを確認
  • ローカル開発版では、設定ひな型を作るinit、事前診断のdoctor、日本語の進捗・結果表示を追加。これらのCLI改善は、上記日時点ではGitHubへ未反映
  • CLI改善を含むローカル開発版で67件のテストが成功。CloudFront APIは模擬応答で、正常な取得と権限不足を検証

07

制約と次の一手

  • 初期版はReact／Viteの静的SPAが対象。Node.js 24以降とLinux／WSLが必要で、アプリ側のビルドIDや操作シナリオの準備も必要
  • 検証は1実行拠点・実行時点の指定した操作に限る。CloudFrontの全配信拠点や、将来のキャッシュミス時の成功を保証するものではない
  • SSR、Service Worker、APIの新旧互換性、自動ロールバックは未対応
  • 実AWS環境での動作確認は未実施。次は所有するステージング環境で試し、導入にかかる手間と、実際の更新時の検出結果を確かめる
